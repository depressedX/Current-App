# MVP 推荐方案

状态：方案，尚未实现。当前 App 仍为随机选歌，反馈只保存。

## 选择

采用 **内容特征筛选 + 个人偏好加权排序**。

先用规则跑通「表达需求 → 听歌 → 反馈 → 后续调整」。不训练推荐模型，暂不接入 Contextual Bandit。
候选范围先限定为用户收藏和选定歌单，不做全网推荐。

## 三类数据分开

| 数据 | 示例 | 更新方式 |
|---|---|---|
| 歌曲特征 | Rock、阴郁倾向、能量、BPM、人声 | 音频分析、外部数据、人工修正 |
| 个人偏好 | 喜欢某首歌、偏爱某种声音 | 用户明确反馈 |
| 当前意图 | 今天想听阴郁摇滚，但别太激烈 | 自然语言输入、本次调整 |

歌曲特征保留来源、置信度和版本；缺失为未知。
爱心增加个人偏好，不修改歌曲属性，永不同步网易云收藏。
临时需求不直接覆盖长期口味。

## 流程

### 1. 准备初始特征

- 风格：Rock、Jazz、House 等多标签。
- 情绪：阴郁、欢快、温暖等倾向分数。
- 能量：平静到激烈。
- BPM、人声／纯音乐。

音频模型提供初始判断，不是对主观感受的最终结论。
「阴郁」不简单等于悲伤；听感情绪与歌词情绪分开。

### 2. 解析当前需求

输入：「阴郁的摇滚，别太激烈。」

| 条件 | 处理 |
|---|---|
| 摇滚 | 限定候选风格；置信度不足时不声称确定匹配 |
| 阴郁 | 按情绪匹配度排序 |
| 别太激烈 | 高能量降分 |
| 明确 BPM 区间 | 按区间过滤；未知项不冒充满足条件 |

自然语言解析与选歌排序分开。初期可先支持少量表达，再增加模型解析。
候选不足时告知用户并提供放宽条件的选择，不悄悄忽略要求。

### 3. 排序并组成队列

概念评分：

> 当前需求匹配度 + 个人偏好 − 重复与疲劳惩罚

- 当前需求优先于长期偏好。
- 爱心首先提高这首歌的偏好权重，对相似歌曲只小幅加分。
- 连续重复同一歌曲或过于相似的歌曲要降分。
- 保留少量符合本次条件的新歌作为探索。
- 系数、探索比例和冷却时间先设为可调整配置，不把示例数值当作结论。

### 4. 接收反馈，调整尚未播放的队列

| 反馈 | MVP 处理 | 作用范围 |
|---|---|---|
| 喜欢 | 增加歌曲偏好，小幅提高相似歌曲排序 | 个人偏好，保留当时场景 |
| 不够阴郁／太激烈 | 调整对应情绪或能量要求 | 当前听歌场景 |
| 风格不对 | 降低歌曲与本次风格要求的匹配度 | 个人匹配记录，不直接改全局标签 |
| 这次不想听 | 暂时排除这首歌 | 当前会话 |
| 听腻了 | 在冷却期减少出现 | 有时效的歌曲偏好 |
| 下一首 | 先只切歌，不推断原因 | 当前队列 |
| 未说明原因的不合适 | 保留事件，暂时排除歌曲，不猜测具体维度 | 当前会话 |

当前 UI 的「情绪不太对」没有方向，不能据此自动推断要更阴郁还是更明快。
要实现定向调整，需补充「不够阴郁／太激烈」等明确反馈，或允许用户直接修改需求。

反馈针对操作时的歌曲和场景，不因自动切歌而错记到下一首。
同一状态下重复点击不应无限累加权重。

## 例子

用户想听阴郁摇滚，喜欢了两首低能量歌曲，又反馈另一首「太激烈」。

后续优先选择：

1. 仍符合阴郁摇滚要求。
2. 能量更低。
3. 与喜欢的歌曲有一定相似性。
4. 最近没有反复出现。

这次调整只需更新门槛和排序权重，不需要重新训练音频模型。
不能由一次不喜欢推断用户讨厌整个 Rock 风格。

## 保留的记录

- 本次需求及解析条件。
- 候选歌曲、最终顺序和主要评分项。
- 推荐歌曲、用户反馈、时间和账号。
- 特征来源与模型版本。
- 将来引入随机探索时，记录选择概率，供策略评估。

不记录登录 cookie。用户可清除本机历史与反馈。

## 实施顺序

1. 建立歌曲特征与偏好数据，保留未知和置信度。
2. 做基础筛选和可解释排序，替换随机生成器。
3. 接入明确反馈，调整尚未播放的队列。
4. 用真实歌单验证，再调系数和探索比例。
5. 有足够交互后，再评估 Contextual Bandit 是否有收益。

## 验收

- 「太激烈」之后，后续歌曲能量降低，风格要求仍保留。
- 爱心提高偏好，但不压过本次明确条件，也不导致重复刷屏。
- 下一首不产生负向风格标签。
- 本次排除不变成永久不喜欢；听腻惩罚可随时间消退。
- 同一已喜欢状态不因连点无限增权。
- 推荐结果能解释主要匹配条件；未知数据不会被当作已满足。
- 无任何网易云收藏同步请求。

本方案的判断标准：用户是否更快找到此刻想听的音乐，而不是播放时长是否更长。
